# 悍匠统一门户、资料库与资源平台总体实施计划

> 文档状态：初版规划，供项目负责人拆分任务并交给其他 AI 实施。
>
> 当前唯一实施阶段：**内网资料库 MVP**。在资料库完成验收前，不并行开发公网门户、统一登录、NFC 或新的资源模块。

## 1. 项目目标

最终建设一套用户体验统一、网络权限分层的平台：

1. 用户在任意网络中访问公网门户，查看团队介绍、获奖、项目、公告和允许公开的队员资料。
2. 用户使用统一队员账号登录公网门户，进入个人工作台。
3. 用户连接校园网或指定局域网后，从同一工作台进入内网资料库、资源管理系统和其他内部应用。
4. NFC 队员卡只保存随机入口地址，刷卡后按登录身份、权限和网络环境展示相应内容。
5. 内部文件、库存、借用记录和队员隐私数据不经公网门户反向代理，不直接暴露在互联网。

## 2. 已知条件与约束

- 已有一台可以长期运行的校内服务器。
- 大概率不能配置校园网 DNS，内网应用第一阶段使用固定内网 IP 和端口。
- 暂无正式域名和云服务器，公网门户未来先用免费托管平台提供的二级域名试运行。
- 当前仓库是 Next.js 15、React 19、Prisma 和 SQLite 单体应用。
- 当前已有管理员、操作员账号，以及电机建档、标签、扫码出入库、审批和日志能力。
- 当前系统仍是内网试点，不允许直接暴露到公网。

## 3. 总体架构

### 3.1 逻辑上统一，网络上分区

```text
互联网
  └─ 公网统一门户（未来）
       ├─ 团队展示
       ├─ 登录与个人工作台
       ├─ NFC 公开入口
       └─ 内网应用入口

校园网/局域网
  └─ 内网应用服务器（已有）
       ├─ 资料库（当前优先）
       ├─ 资源管理系统（已有电机模块）
       ├─ 队员内部档案（后续）
       └─ 文件存储与备份
```

公网门户可以显示内网入口，但不代理内网请求。处于外部网络时入口显示“仅校园网可用”；处于校园网时浏览器直接连接内网服务器固定 IP。

### 3.2 数据边界

| 数据 | 存放位置 | 是否允许公网 |
|---|---|---|
| 团队介绍、获奖、公开项目 | 公网内容库 | 是 |
| 经本人同意的公开队员资料 | 公网内容库 | 是 |
| 资料库文件、内部制度、图纸、源码包 | 内网存储 | 否 |
| 资源库存、借用、维修和审批记录 | 内网数据库 | 否 |
| 队员手机号、学号、内部经历和权限 | 内网数据库 | 否 |
| NFC 随机卡片标识 | 公网可保存映射，敏感详情仍在内网 | 仅标识可公开 |

## 4. 强制实施顺序

| 阶段 | 名称 | 前置条件 | 完成标志 |
|---|---|---|---|
| 1 | 内网资料库 MVP | 当前仓库可运行 | 真实资料试用通过且完成恢复演练 |
| 2 | 队员中心与权限基础 | 资料库验收 | 队员账号、角色、公开字段边界稳定 |
| 3 | 公网门户 MVP | 队员数据边界确认 | 免费公网地址可稳定访问 |
| 4 | 统一登录与内网入口 | 门户和队员中心稳定 | 同一账号安全进入内网应用 |
| 5 | NFC 队员卡试点 | 统一身份与公开字段稳定 | 3 至 5 张卡完成挂失、换卡和权限测试 |
| 6 | 资源平台扩展 | 前述基础稳定 | 扩展裁判设备、耗材等模块 |

任何阶段未通过验收，不得以“先占位”为理由同时启动后续阶段。

# 第一阶段：内网资料库 MVP

## 5. 阶段目标

让队员能够在校园网中安全地完成下面的闭环：

```text
登录 -> 上传资料 -> 填写标题和分类 -> 搜索 -> 查看详情 -> 下载 -> 留下审计记录 -> 备份与恢复
```

第一阶段解决的是“资料在哪里、谁可以看、能不能找到、丢了能不能恢复”，不是建设完整的在线协作文档平台。

## 6. MVP 范围

### 6.1 必须实现

- 资料列表、分页和空状态。
- 按标题、说明、原文件名进行关键词搜索。
- 按分类、标签、上传人和更新时间筛选。
- 上传单个文件并录入标题、说明、分类、标签和可见范围。
- 资料详情页展示元数据，不直接暴露服务器文件路径。
- 通过鉴权接口下载文件。
- 管理员可以编辑元数据、停用资料和恢复误停用资料。
- 上传、下载、编辑、停用、恢复操作写入审计日志。
- 管理员维护分类和标签。
- 文件与数据库一起备份，并完成至少一次恢复演练。
- 桌面浏览器可用，手机端能够搜索、查看详情和下载。

### 6.2 明确不做

- 不做公网访问资料库。
- 不做在线编辑 Word、Excel、PPT 或 CAD。
- 不做多人实时协作。
- 不做全文解析和 OCR。
- 不做评论、点赞、收藏和推荐。
- 不做复杂版本对比。
- 不做断点续传和超大文件分片上传。
- 不在第一阶段迁移 PostgreSQL、MinIO 或 NAS；先保留清晰的替换接口。
- 不把资料发布到公网门户。

## 7. 技术方案

### 7.1 集成方式

资料库作为当前 Next.js 应用的独立模块实现：

```text
/library                 资料列表与搜索
/library/new             上传资料
/library/[id]            资料详情
/library/[id]/edit       编辑元数据
/admin/library           资料库管理
/admin/library/categories 分类管理
/admin/library/audit     审计日志
/api/library/[id]/download 鉴权下载
```

复用当前 `User`、登录状态和页面壳。不要复制一套新的登录系统。

### 7.2 文件存储

- 默认目录：`storage/library/`。
- 目录不得位于 `public/` 下。
- 数据库只保存相对存储路径，不保存客户端提交的绝对路径。
- 实际存储文件名使用随机 UUID；原始文件名只作为元数据保存。
- 下载必须经过服务端权限校验，并设置 `Content-Disposition: attachment` 和 `X-Content-Type-Options: nosniff`。
- 默认单文件上限 50 MiB，通过环境变量配置。
- 第一版禁止上传可执行或主动脚本文件，例如 `exe`、`msi`、`bat`、`cmd`、`ps1`、`js`、`html`。
- 允许的办公文档、图片、压缩包、文本和常见工程文件采用扩展名白名单；不能只信任浏览器提供的 MIME 类型。
- 保存时计算 SHA-256，用于完整性检查和辅助识别重复文件。
- 文件写入成功后才能提交数据库记录；数据库失败时必须清理孤儿文件。

### 7.3 数据模型建议

字段名可在实现时按 Prisma 规范微调，但语义不得静默改变。

#### LibraryCategory

- `id`
- `name`
- `slug`，唯一
- `description`
- `parentId`，第一版界面可以只支持一级分类，但结构允许父分类
- `sortOrder`
- `isActive`
- `createdAt`、`updatedAt`

#### LibraryDocument

- `id`
- `title`
- `description`
- `originalFileName`
- `storedFileName`
- `storagePath`
- `fileExtension`
- `mimeType`
- `fileSize`
- `sha256`
- `categoryId`
- `visibility`：第一版为 `all_members` 或 `admins_only`
- `status`：`active` 或 `archived`
- `uploaderId`
- `createdAt`、`updatedAt`、`archivedAt`

#### LibraryTag

- `id`
- `name`，唯一
- `slug`，唯一
- `createdAt`

#### LibraryDocumentTag

- `documentId`
- `tagId`
- 复合唯一约束

#### LibraryAuditLog

- `id`
- `documentId`，允许资料被移除后保留日志
- `actorId`
- `action`：`upload`、`download`、`update`、`archive`、`restore`
- `detail`，只记录必要信息，不能写密码、令牌或完整文件内容
- `createdAt`

### 7.4 初始权限

| 操作 | 管理员 | 操作员 |
|---|---:|---:|
| 浏览普通资料 | 是 | 是 |
| 下载普通资料 | 是 | 是 |
| 浏览管理员资料 | 是 | 否 |
| 上传资料 | 是 | 是 |
| 编辑自己上传资料 | 是 | 第一版否 |
| 编辑任意资料 | 是 | 否 |
| 停用和恢复资料 | 是 | 否 |
| 管理分类和标签 | 是 | 否 |
| 查看审计日志 | 是 | 否 |

后续队员中心完成后，再把 `operator` 替换为更细的部门、项目和角色权限。第一阶段不要自行引入复杂 ACL。

### 7.5 初始分类建议

- 团队制度
- 赛季与比赛规则
- 机械与 CAD
- 电控与嵌入式
- 视觉与算法
- 宣传与设计
- 培训资料
- 采购与供应商资料
- 历届项目归档
- 其他

管理员可以调整分类；代码和测试不能依赖中文分类名称。

## 8. 资料库实施批次

### L0：基线与设计冻结

任务：

- 在干净环境验证现有安装、测试、类型检查和生产构建。
- 记录数据库和上传目录现状。
- 冻结 URL、权限表、字段、文件上限和允许类型。
- 给 `storage/` 添加正确的 Git 忽略规则，只保留必要的目录说明文件。

验收：不改变现有业务；基线命令和结果写入阶段记录。

### L1：数据库与安全存储

任务：

- 添加资料库 Prisma 模型和迁移。
- 实现存储配置、随机文件名、路径约束、大小限制、扩展名校验和 SHA-256。
- 实现事务补偿，防止数据库记录和实际文件不一致。
- 为存储和权限核心逻辑编写单元测试。

验收：不能通过构造文件名越权读取其他路径；失败上传不残留文件或数据库记录。

### L2：上传、列表、详情与下载闭环

任务：

- 实现 `/library`、`/library/new`、`/library/[id]`。
- 实现鉴权下载接口。
- 在桌面导航和移动端导航加入“资料库”。
- 上传和下载写入审计日志。

验收：管理员和操作员均可完成一次真实文件的上传、搜索、详情和下载，下载内容哈希与原文件一致。

### L3：分类、标签、筛选和管理

任务：

- 实现分类和标签管理。
- 实现关键词、分类、标签、上传人、时间筛选和分页。
- 实现管理员编辑、停用和恢复。
- 搜索条件保留在 URL 查询参数中，方便复制链接和返回列表。

验收：组合筛选结果正确；停用资料不出现在普通列表但管理员可恢复。

### L4：权限、审计与安全回归

任务：

- 覆盖 `all_members`、`admins_only` 两种可见范围。
- 对页面、Server Action 和 API 分别做服务端权限检查。
- 管理员查看审计记录。
- 验证越权下载、伪造 ID、被停用账号、已归档文件和异常文件名。

验收：隐藏按钮不算权限控制；直接请求 URL 或 API 同样无法越权。

### L5：备份、恢复与部署

任务：

- 扩展备份脚本，同时备份数据库、资料文件和清单。
- 清单至少包含备份时间、数据库文件、文件数量、总大小和校验信息。
- 文档化恢复步骤。
- 在临时目录完成一次恢复演练并抽查文件哈希。
- 确保 systemd 服务对 `storage/library` 具有最小必要读写权限。

验收：仅有备份文件但没有做过恢复，不算通过。

### L6：真实试用与冻结

任务：

- 选择 20 至 50 份真实资料导入。
- 邀请至少一名管理员和两名普通队员试用。
- 收集上传、分类、搜索、下载和手机体验问题。
- 只修复阻塞使用和明显安全问题，不在本阶段加入新功能。

验收：连续试用一周无数据丢失；负责人签字确认资料库 MVP 完成。

## 9. 资料库总体验收清单

- [ ] 未登录用户无法查看列表、详情和下载。
- [ ] 操作员无法查看 `admins_only` 资料。
- [ ] 直接猜测下载地址无法绕过鉴权。
- [ ] 上传文件不位于 `public/`。
- [ ] 路径穿越、超限文件和禁止扩展名被拒绝。
- [ ] 资料可以按标题、原文件名、分类和标签找到。
- [ ] 上传、下载、编辑、停用和恢复都有审计记录。
- [ ] 停用不物理删除文件，避免误操作造成不可恢复损失。
- [ ] 数据库和资料文件在同一备份周期内保存。
- [ ] 已执行恢复演练并验证文件哈希。
- [ ] `npm test`、`npm run lint`、`npm run build` 全部通过。
- [ ] 现有电机建档、查询、入库、出库和审批没有回归。

# 后续阶段规划

## 10. 第二阶段：队员中心与权限基础

目标：建立所有后续系统共同使用的队员身份和权限来源。

主要能力：

- 队员档案、头像、部门、技术方向、入队年份、在队状态。
- 账号与队员档案关联。
- 公开字段和内部字段分离。
- 队员本人确认哪些资料可以公开。
- 管理员、资料管理员、资源管理员、普通队员等角色。
- 离队、停用、重新加入和权限变更审计。

退出条件：现有资源记录、资料上传人和队员档案能够稳定关联，隐私字段清单经过负责人确认。

## 11. 第三阶段：公网门户 MVP

目标：用免费托管地址上线可公开访问的统一入口。

主要能力：

- 团队首页、介绍、发展历程。
- 获奖记录、项目展示、新闻公告。
- 公开队员名片。
- 登录与个人工作台。
- 内网资料库、资源管理系统入口。
- 外部网络访问内网入口时的明确说明。

实施前先在校园网、移动网络和家庭网络测试 Cloudflare Pages、EdgeOne Pages 等候选平台，不把托管商名称写死在业务代码中。

退出条件：公开数据与内部数据物理或逻辑分离；公网服务无法直接查询内网数据库和文件目录。

## 12. 第四阶段：统一登录与内网入口

目标：用户在公网门户登录后，位于校园网时能够安全进入内网应用。

推荐方式：标准 OAuth 2.1 / OpenID Connect 授权码流程配合 PKCE，使用短期一次性授权码。禁止把长期 JWT 放在 URL 中。

在无法配置校内 DNS 的情况下：

- 内网服务器使用固定 IP 或 DHCP 地址保留。
- 门户入口指向内网 HTTPS 地址。
- 浏览器不能可靠判断校园网状态，入口可始终显示，连接失败时给出说明。
- 不使用公网反向代理或隧道把资料库暴露出去。

退出条件：登录重放、伪造回调、开放重定向、账号停用和权限变更均有测试。

## 13. 第五阶段：NFC 队员卡

目标：通过 NFC 卡进入统一队员页面，并按身份和网络环境展示内容。

规则：

- 卡片仅写入随机、不可枚举的 HTTPS 地址。
- 不把姓名、手机号、学号、权限或文件写入卡片。
- 不依赖手机浏览器读取芯片 UID。
- 未登录仅显示本人同意公开的资料。
- 登录后显示相应个人中心和内网入口。
- 支持发卡、停用、挂失、换卡和操作审计。
- 免费托管二级域名仅用于 3 至 5 张测试卡；批量发卡前购买团队长期控制的域名。

退出条件：完成安卓和 iPhone 测试，以及丢卡、挂失、复制链接、越权和换卡测试。

## 14. 第六阶段：资源平台扩展

在保留现有电机闭环的基础上，逐步抽象通用资产、分类、库位和流转模型，再扩展：

1. 裁判系统设备。
2. 工具和固定资产。
3. 打印耗材和库存预警。
4. 维修、报废和盘点。
5. 打印申请、审核和成本记录。

每次只扩展一个真实业务域，完成现场试用后再进入下一个。

# 交给其他 AI 的执行规则

## 15. 单任务交付协议

每次只给 AI 一个编号明确的任务，例如“只实现 L1 数据库与安全存储”。任务提示中必须包含：

1. 阅读本计划和 `docs/AI_HANDOFF.md`。
2. 检查工作区和现有代码，不覆盖无关改动。
3. 复述本次范围、非目标和验收标准。
4. 先提交实施方案，再修改代码。
5. 不静默改变字段、权限、URL 或安全边界。
6. 为新增核心逻辑补测试。
7. 运行与风险相称的测试、类型检查和构建。
8. 更新 `docs/AI_HANDOFF.md`，记录实际结果、决策、遗留问题和下一步。
9. 停止在本任务验收边界，不顺手开始下一批。

```text
- 保留无关的用户改动。
- 不改变已冻结的架构和权限；发现冲突时停止并报告。
- 完成后运行测试、类型检查和生产构建。
- 更新 docs/AI_HANDOFF.md，写明修改文件、验证结果、剩余风险和下一任务建议。
```

## 17. 决策升级规则

其他 AI 遇到下面情况必须停止并交回项目负责人决定：

- 需要把资料库开放到公网。
- 需要使用内网穿透或公网反向代理。
- 需要更换数据库、认证体系或部署平台。
- 需要物理删除已有资料。
- 需要改变公开信息和个人隐私边界。
- 需要引入付费服务。
- 需要一次性迁移大量真实数据。
- 发现现有安全问题会使继续实施产生明显风险。

## 18. 项目状态维护

长期项目不依赖一条持续膨胀的聊天记录。以 `docs/AI_HANDOFF.md` 作为当前事实来源：

- 只记录当前阶段、已确认决策、最近完成、验证结果、阻塞和下一任务。
- 完成一个任务就压缩更新一次。
- 开新对话时只提供主计划和该状态文件；旧对话仅在需要查证细节时参考。
- 主计划用于描述目标和边界，状态文件用于描述实际进度，两者不得混用。
